# vcftools-ng v0.11.0

Status: **complete for adaptive Plain/TBI/CSI input and the cumulative
v0.10 compatibility surface**.

v0.11.0 replaces the single full-file reader with a deep
`OrderedShardSource` module. Callers consume stable ordered batches; three
adapters hide container-specific input behavior.

## Input and execution additions

- `--input-backend auto|stream|plain|indexed`
- automatic detection from the actual HTSlib format and compression type;
- Plain VCF aligned byte ranges read independently with `pread`;
- BGZF VCF plus TBI/CSI split into ordered coordinate regions;
- BCF plus CSI split into ordered coordinate regions;
- record-start ownership removes overlap-query duplicates;
- persistent per-worker HTSlib input/index/header contexts;
- bounded ordered-ahead memory;
- index record counts and requested batch size determine shard density;
- scheduler, CPU-affinity, and hardware-aware default thread discovery;
- total CPU budget divided between input, HTSlib I/O, and compute stages;
- selected backend, planned shards, and effective stage concurrency logged.

Automatic mode falls back to the HTSlib ordered stream when no direct adapter
is available. Forced backends form the compatibility-test seam.

## Exact ordering

Plain ranges move interior offsets to the next full newline. Indexed regions
follow index contig order, preserve iterator order within each region, and
accept a record only when its start position belongs to that half-open
region. Completed shards may arrive out of order but are exposed to the
pipeline by stable ordinal.

Consequently the existing ordered commit still owns thinning, floating-point
accumulation, window boundaries, LD/PCA site order, and record writing. The
full v0.10 surface—including `--thin`, π, Tajima's D, FST, LD, PCA, recode,
FILTER/INFO/FT, and individual statistics—passed after the indexed adapter
was enabled.

## Compatibility validation

- Oracle: VCFtools 0.1.17.
- Main fixture: 2,300,000 real records, 23 chromosomes, 412 samples.
- Semantic fixture: 23,000 real FILTER/INFO/FT records.
- Standard gates: original plus 8 and 16 threads.
- Full `ctest`: 2/2 passed; input-backend differential test 2.29 seconds, cumulative compatibility test 107.34 seconds.
- Backend differential: stream, indexed BGZF VCF, indexed BCF, and Plain VCF
  counts were byte-identical.
- Five-scenario benchmark: all ten 8/16 outputs had the same SHA256 as their
  original output.
- Additional compatibility-only smoke: indexed BGZF VCF, indexed BCF, and
  Plain VCF completed at `--threads 256` with byte-identical counts.

The 256-thread smoke is not a performance claim. It verifies that worker,
shard, header/index context, and ordered-publication code paths do not contain
a 16/32-thread compatibility cap.

## Interpretation

The indexed VCF and Plain results validate the architecture borrowed from
`VensinMa/vcf2phylip`: input itself must have independent readers. Increasing
only compute or decompression threads cannot remove a serial text parser.

The BCF stream continues to scale because HTSlib can decompress BGZF blocks
in parallel and BCF record decoding is compact. The CSI adapter improves
scaling further by adding independent ordered readers.

The unindexed BGZF VCF result intentionally remains visible. Its next adapter
must scan BGZF block headers, decompress blocks in parallel, stitch records
that cross blocks, and publish complete records in block order.
