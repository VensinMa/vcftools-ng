# vcftools-ng v0.11.4 implementation plan

Status: **implemented as v0.11.4-dev; not approved for release**.

The permanent process changed after the initial investigation. Daily
optimization now uses only BGZF+TBI, Plain VCF, and BCF+CSI and reuses a
hash-locked Original baseline. Automatic-index and no-auto-index scenarios
run only for an explicitly approved release candidate. See
[`docs/benchmark-workflow.md`](../benchmark-workflow.md).

Implemented development slices include:

- overlapping input and compute lanes for the real seven-filter workload;
- automatic CSI inspection/construction at every requested thread count;
- rotational-storage detection and bounded page-cache prefetch;
- `--stdout` recode for the normal `vcftools | bgzip` workflow;
- direct fused `--freq`, `--freq2`, `--counts`, `--missing-site`,
  `--site-depth`, `--site-mean-depth`, and `--site-quality`;
- BCF-to-VCF recode compatibility for Original 0.1.17 header, missing-GT,
  and Character/String FORMAT quirks.

The initial seven-scenario 2.3-million-record run is retained under
`benchmarks/results/v0114-real-filter-subset`. All 42 candidate outputs
(seven scenarios × six thread counts) passed byte comparison. Its three
Original VCF outputs remain locally stored as the permanent 34 GB golden set.

## Primary real-project workload

All v0.11.4 scheduling and backend decisions are evaluated with:

```text
--min-alleles 2 --max-alleles 2
--minGQ 10 --minQ 30
--min-meanDP 7 --max-missing 0.9 --maf 0.1
```

The primary output is `--recode --recode-INFO-all`, matching the common
filter-and-bgzip workflow. Filtered `--counts` is retained only as a compact
diagnostic artifact for rapid `cmp` gates; it is not the headline performance
workload.

The seven established scenarios remain BGZF+TBI, BGZF+automatic-CSI,
BGZF+`--no-auto-index`, Plain VCF, BCF+CSI, BCF+automatic-CSI, and
BCF+`--no-auto-index`.

## Primary deepening: overlapping shard execution

v0.11.3 divided a fixed thread budget between input and compute. For text
inputs, approximately 75% became input workers and 25% became filtering
workers. The complete-data real-filter measurements consequently used only
about one CPU at `--threads 2`, 4–5 CPUs at `--threads 8`, 7–8 at
`--threads 16`, and 12–18 at `--threads 32`.

v0.11.4 treats `--threads` as the ordered-shard concurrency target and runs a
smaller bounded compute lane behind it. Input parsing, GT/DP/GQ decoding,
filtering, and ordered output overlap instead of being forced to share a
zero-sum worker split. On the 2.3-million-record BGZF+TBI probe, all outputs
were byte-identical and the results changed as follows:

| Threads | Split-pool wall | Overlapped wall | CPU after | Speedup vs Original |
|---:|---:|---:|---:|---:|
| 2 | 73.23 s | 39.23 s | 216% | 3.18× |
| 4 | 38.84 s | 21.91 s | 393% | 5.70× |
| 8 | 21.77 s | 13.69 s | 686% | 9.12× |
| 16 | 13.87 s | 9.19 s | 1217% | 13.59× |
| 32 | 9.38 s | 6.39 s | 2088% | 19.55× |

Original took 124.90 seconds. One-thread vcftools-ng took 73.41 seconds
(1.70×) and was also byte-identical.

The bounded prefetch window and batch slots remain the memory backpressure
seams. File-descriptor limits and the detected process CPU allocation cap
large-server concurrency.

## Evidence from v0.11.3

The final 11,230,392-record matrix shows that direct text-to-count fusion is
the highest-leverage path:

- BGZF + TBI reaches 35.46× at 32 threads.
- Plain VCF reaches 1.81× at one thread and 7.82× at 32 threads.
- No-index BGZF reaches 3.04×–5.99× without requiring an index.
- Every 1/2/4/8/16/32-thread configuration is faster than Original.

The same direct parser currently serves only `--counts`. `--freq`,
`--missing-site`, `--site-depth`, and `--site-mean-depth` request data already
present in the same VCF record but fall back to the generic `bcf1_t` pipeline.
The historical real-subset measurements show about 67–75 seconds per
standalone Original scan for these outputs, while the old combined
no-index-BGZF path still took about 56 seconds.

## Secondary deepening: common site statistics

### SiteStatPlan Module

Replace the counts-only eligibility decision with a compiled plan for these
unfiltered site-local outputs:

- `--freq`
- `--counts`
- `--missing-site`
- `--site-depth`
- `--site-mean-depth`
- `--site-quality`

The Interface states which artifacts are requested and whether GT, DP, or QUAL
must be decoded. The Implementation parses FORMAT once and traverses each
sample once per accepted variant. Adding or removing one output must not add
another record scan.

Exact compatibility rules remain inside this Module:

- GT is limited to the oracle-compatible haploid/diploid behavior already
  enforced by the fused counts path.
- An absent GT field contributes two missing alleles per sample to
  `--missing-site`, matching VCFtools 0.1.17.
- DP uses the first scalar, excludes missing and negative values, and preserves
  the oracle's unsigned sums and sample variance formula.
- floating output uses six significant digits and preserves `-nan`.
- input order, chromosome spelling, allele spelling, and artifact headers are
  unchanged.

### OrderedArtifactSet Module

Replace the single `.frq.count` stream and single string per shard with a
plan-sized artifact set. Each ordered shard owns one buffer per requested
artifact. The committer appends all buffers for ordinal *N* before ordinal
*N+1*. Plain VCF, indexed BGZF, and streaming compressed VCF reuse the same
Interface.

This gives leverage across six outputs and three text input adapters, while
keeping header, suffix, open failure, write failure, and ordering knowledge in
one place.

## Backend and storage policy

- Plain VCF: aligned byte-range workers.
- BGZF with valid TBI/CSI: ordered tabix windows from the existing adaptive
  backend at every thread count.
- BGZF without an index: direct stream with HTSlib decompression overlap.
- BCF: retain the generic ordered pipeline in this release.
- `--no-auto-index`: unchanged and never creates an index.
- existing valid CSI/TBI: unchanged and never overwritten.

Without `--no-auto-index`, every BGZF VCF or BCF invocation validates CSI/TBI
at every thread count, builds CSI only when no sidecar exists, and then enters
the indexed backend. Existing valid or invalid sidecars are never overwritten.

Plain VCF cannot be indexed. On SSD/NVMe, disjoint aligned ranges maximize
bandwidth and the operating-system page cache already uses available RAM. On
rotational local storage, random range reads can be slower than one sequential
pass. v0.11.4 therefore detects rotational block devices when Linux exposes
that information and uses a low-seek sequential range adapter; unknown,
network, and virtual filesystems keep the explicit `--input-backend` override.
Copying a 12–123 GB VCF into a second user-space buffer is not assumed to be
faster than the page cache.

## Compatibility gates

1. Synthetic VCF containing:
   - GT first, middle, last, and absent;
   - phased, unphased, haploid, partially missing, and fully missing GT;
   - DP first, middle, last, absent, and missing;
   - multiallelic and ALT=`.`;
   - finite and missing QUAL;
   - zero and one valid DP values to exercise `-nan` variance.
2. Each of the six outputs separately against an Original-generated golden.
3. All six outputs in one vcftools-ng scan against the six separate goldens.
4. Plain VCF and BGZF at 1/2/4/8/16/32 threads.
5. Indexed BGZF, automatic CSI, and `--no-auto-index`.
6. Polyploid rejection and corrupt/stale index behavior remain covered.
7. Full cumulative CTest and ASan/UBSan.
8. The 2,300,000-record real subset with the seven project filters in all
   seven established input/index scenarios.
9. Filtered recode with all INFO retained, including `--stdout`, against the
   Original recode bytes.

Every output must pass `cmp`; numeric tolerance is not accepted.

## Benchmark gate

The primary v0.11.4 workload is the seven-filter recode workload above.
Filtered counts is a compact tuning probe. The secondary common-stat workload
is `--freq --counts --missing-site --site-depth --site-mean-depth`; because
VCFtools 0.1.17 permits only one output function per invocation, that Original
baseline is the strictly serial sum of five scans while vcftools-ng produces
all five artifacts in one scan.

Record, for 1/2/4/8/16/32 threads:

- wall time;
- user and system CPU time;
- mean CPU utilisation;
- maximum RSS;
- speedup against the summed Original baseline;
- SHA-256 and byte-comparison result for every artifact.

The full 11,230,392-record matrix is deferred until the implementation and
real-subset gate are stable. A full-data v0.11.4 candidate run is required
before release only for paths whose implementation changed; unchanged BCF
rows may reuse their hash-validated evidence.

## Release criteria

- No regression in the v0.11.3 unfiltered `--counts` 1–32-thread gate.
- Every seven-filter diagnostic and recode artifact is byte-identical.
- Automatic indexing is consistent at 1/2/4/8/16/32 threads.
- Rotational-storage policy is reported and can be overridden.
- Every new fused artifact is byte-identical.
- Every changed scenario beats its Original seven-filter baseline at every
  tested thread count.
- Version history, benchmark TSV, README, technical record, portable Linux
  x86_64 package, master, and GitHub Release are updated together.
