# vcftools-ng v0.13.0 — Transactional BGZF Output and Hot-Path Acceleration

## Scope

Status: **released after the complete 108/108 first-repeat full-data gate;
follow-up repeats are in progress**.

v0.13.0 is the reliability, disk-safety, and hot-path efficiency release.
It keeps VCFtools 0.1.17 as the compatibility oracle and does not introduce a
fast-math, direct-`bcf_fmt_t`, BLAS replacement, or lossy output mode.

## Reliability and packaging

- Scientific outputs are staged, checked through flush/close, and published
  as one transaction; failure preserves every previous destination.
- stderr remains usable when the optional log mirror fails.
- Every floating-point option rejects NaN and infinity.
- Scheduler allocation, CPU affinity, cgroup quota, online CPUs, and the
  file-descriptor ceiling are intersected. Automatic selection is capped at
  128; an explicit request is not subject to that automatic ceiling.
- File-based `--recode` now writes BGZF VCF by default. `--recode-vcf`
  explicitly selects Plain VCF and `--recode --stdout` remains plain text.
- The portable archive exposes only `bin/vcftools-ng`. Its private indexing
  helper is `libexec/bcftools.bin`.
- Portable dependency sources and SHA-256 values are locked to bcftools 1.24
  and HTSlib 1.24.

## Hot-path changes

1. An immutable `ExecutionPlan` is compiled once. GT/DP/GQ/FT requirements
   and filter/output switches are no longer rebuilt for every site.
2. Raw mean-DP accumulation, GQ/DP/FT genotype masking, and accepted-depth
   statistics share one selected-sample pass. DP is decoded from the scratch
   buffer once per sample in that pass.
3. Recode-only work no longer allocates chromosome and allele strings that no
   consumer reads.
4. Accepted VCF lines are appended to one ordered batch blob. Plain and BGZF
   writers receive one blob per committed batch while thinning and record
   order remain controlled by the same ordered-commit lane.
5. Each BGZF compression worker owns one long-lived zlib stream and resets it
   between blocks. Compression level, raw-DEFLATE parameters, BGZF framing,
   block order, and output bytes are unchanged.
6. Plain VCF range workers retain one read-only descriptor and use `pread`
   across assigned aligned ranges instead of opening and closing every shard.
7. Indexed/Plain text parsing receives an input-heavy adaptive share of the
   strict total CPU budget. At least two compute lanes are retained from eight
   threads upward and compute capacity grows with the requested budget.
8. The direct Plain/BGZF text kernel now implements the real
   seven-filter workload (`--min-alleles`, `--max-alleles`, `--minGQ`,
   `--minQ`, `--min-meanDP`, `--max-missing`, and `--maf`) together
   with site-statistics and VCF recode outputs. GT/GQ/DP parsing, genotype
   masking, call-rate and MAF filtering, exact VCF reconstruction, ordered
   publication, and optional deterministic BGZF compression share one scan.
9. Parallel range sources publish bounded
   `(shard_ordinal, chunk_ordinal)` record chunks while reading. Plain VCF
   uses incremental `pread`; indexed VCF/BCF no longer retains a complete
   decoded shard before downstream compute can begin.

## Decisions from profiling

Simply raising the indexed shard target from roughly 512–630 records to 1,024
reduced the 2.3-million-record BGZF fixture from 3,657 to 2,254 shards, but it
increased wall time from about 11.02 to 11.80 seconds and peak RSS from about
622 MiB to 837 MiB. That experiment was reverted. Larger ordered shards will
only be reconsidered together with incremental
`(shard_ordinal, chunk_ordinal)` publication and byte/record backpressure.

The existing compression-worker allocation policy is unchanged. The release
does not add a fixed 12–16 thread ceiling and does not use `-ffast-math`.

## Candidate validation

- Release build and complete CTest suite: PASS, 7/7 (360.32 seconds).
- Fresh ASan/UBSan build and complete CTest suite: PASS, 7/7 (584.68 seconds),
  with no sanitizer finding.
- The new seven-filter fused path has a dedicated Plain/BGZF-vs-BCF
  differential gate at 1, 4, and 32 threads: PASS.
- Direct seven-filter recode passed the 23,000-site, 412-sample old-engine
  golden for Plain VCF, default BGZF, stdout, INFO retain/remove, simultaneous
  Plain/BGZF output, and combined `--counts + --recode`. The 1/4/8/16/32
  thread outputs were deterministic. An Original-generated edge golden also
  covers sorted multi-value FILTER fields and low-GQ phased, haploid, and
  missing GT values, all of which Original recodes as `./.`.
- On that 23,000-site recode fixture, one-run v0.13.0 versus v0.12.4 BGZF
  wall times were 0.70 vs 0.91 seconds at 4 threads and 0.28 vs 0.61 seconds
  at 32 threads. Every compressed output had identical SHA-256. These are
  development measurements, not a release benchmark.
- A second 23,000-site fixture was extracted from an independent 205-sample
  GATK callset (1,000 records from each of `Chr01`–`Chr23`). It covers 11
  FORMAT tags, 17 INFO tags, nine FILTER definitions, and 5,308 multiallelic
  records. The seven-filter workload retained 1,059 records. Direct VCF
  counts/recode passed the Original oracle at 1/8/32 threads; deterministic
  BGZF decompression and BCF counts also passed.
- That GATK gate exposed one header-only gap: HTSlib formatting injected a
  PASS declaration absent from the source and Original output. Direct recode
  now preserves the raw text VCF header; all DeepVariant-origin goldens remain
  byte-identical after the change.
- On the 230,000-site real development fixture, seven-filter `--counts`
  reduced Plain VCF wall time from the locked v0.12.4 baseline of 1.69 to
  0.91 seconds at 4 threads and from 0.55 to 0.30 seconds at 32 threads.
  BGZF+TBI improved from 7.68 to 1.77 seconds at 4 threads and from 7.43 to
  0.98 seconds at 32 threads. All results had identical SHA-256.
- Existing full differential compatibility suite on the real subset: PASS
  before the final Plain descriptor/thread-allocation tuning; a final rerun is
  required before release.
- Deterministic BGZF output compared with the v0.12.4 binary: identical
  SHA-256 (`038d8fc2fdb7abc5d5d75a7b93818f2bfab9b1e773582ec9b86c5de789f47ec1`)
  on the flagged real fixture.
- The 2.3-million-record BCF exact-recode result is byte-identical to
  `subset-filtered-bcf-recode-info-all.recode.vcf` and to the pre-optimization
  binary.

The complete 11.23-million-record first-repeat release gate passed 108/108
configurations. Every output matched its retained Original scientific golden.
First-repeat application time, durable time, CPU, RSS, output bytes, and the
locked environment are retained in the
[input/output/storage release gate](../../benchmarks/results/v0130-input-output-storage/README.md).
These values are single measurements; follow-up repeats are not yet claimed as
completed means.

The final 5,280,148-byte manylinux2014 portable archive passed clean CentOS 7
and Ubuntu 20.04 verification, including direct private-bcftools dependency
resolution and real automatic CSI construction. Its SHA-256 is
`cb743aa0663afaa78cfc91b4cc82e7d0ef818f09824ee872a403b8713f22a44e`.

The v0.13.0 release matrix covers four input scenarios (BGZF+TBI,
BGZF+automatic CSI, Plain VCF, and adaptive BCF), three same-device output
scenarios, and 1/2/4/8/12/16/24/28/32 requested threads. It uses at most three
repeats. A configuration whose first run exceeds 1,800 seconds runs only once.
Otherwise, a configuration whose first two application-wall times include a
run longer than 600 seconds skips repeat three only when their symmetric
difference is below 10%. Every skip reason and supporting measurement is
retained. Faster or more variable configurations complete all three repeats.
