# vcftools-ng v0.13.1 — Adaptive Zero-Copy Population Analytics

## Scope

Status: **released after locked 23k/230k byte gates and complete Release plus
ASan/UBSan suites; full-data v0.13.0 values are not relabeled**.

v0.13.1 extends the exact direct-text execution family from site-local
filters/statistics and recode to common selection and population analyses.
VCFtools 0.1.17 remains the scientific oracle; no tolerance, fast-math, or
lossy compatibility mode is introduced.

## Runtime implementation

1. Position include/exclude files are loaded once into sorted per-chromosome
   vectors. A shard-local chromosome cursor avoids repeated map lookup while
   preserving Original's POS-only membership semantics.
2. Sample-selection files are resolved against the raw VCF header. Workers
   skip unselected sample fields and decode GT only for the projected sample
   set; selecting every sample uses the identity path.
3. Sample projection and the existing seven-filter direct recode/count engine
   share FORMAT lookup, GT/GQ/DP parsing, filtering, and ordered output.
4. Window pi, Tajima's D, site FST, and window FST workers publish compact
   per-site contributions. The commit lane consumes contributions in fixed
   shard/input order, retaining deterministic floating output.
5. GT-first `FORMAT` and common three-character diploid GT spellings have
   specialized paths with the general parser retained as fallback.
6. Two-population biallelic FST uses fixed stack arrays. The tested
   thread-local flat multiallelic scratch was removed after low-thread
   regressions.
7. Plain VCF workers can parse directly from one shared read-only mapping,
   eliminating kernel-to-user shard copies. Multi-thread runs prefer mapping;
   one-thread mapping is restricted to position/sample-selection workloads.
   Mapping failure falls back to the existing checked `pread` implementation.
8. Backend logs identify `zero-copy mapped aligned ranges` so benchmark and
   support records expose the decision.

At 32 threads, speedup over Original ranges from 8.17x for sparse 1% positions

[230k bilingual report](../../benchmarks/results/workload-matrix-230k-v0130/RESULTS.md).

## Resource tradeoff

The mapped backend exchanges shard copies for file-backed mapped pages. On the
3.20 GB fixture, mapped paths report roughly 3.06 GB peak RSS, while one-thread
pi/Tajima `pread` paths report roughly 133 MiB. File-backed RSS is reclaimable,
but larger inputs and rotational storage still require separate page-fault,
memory-pressure, and wall-time qualification.
